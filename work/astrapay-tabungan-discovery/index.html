Product Discovery: AstraPay Tabungan

Research-led direction setting: design “saving” inside an e-wallet when users frame e-wallets as spending tools.

TL;DR

Mismatch: users treat e-wallet balances as spendable. “Tabungan” inside an e-wallet won’t create saving behavior by default.
Recommendation: build a separated saving pocket (clear boundaries), not a merged wallet balance with perks.

The tension

Shipping a “Tabungan” that behaves like a wallet balance can drive activation but still fail to create real saving intent. Users see e-wallets as payment tools; savings features become “wallet with benefits,” not a true saving product.

Key evidence

  • Users organize money by purpose (mental accounting); saving needs separation.
  • Interest is “nice to have,” not the main driver; trust and control matter more.
  • The payday relocation moment matters: users move funds quickly to a monthly “control center.”

Decision framework

The product fork: balance structure and naming determine whether users perceive this as saving vs spending.

Separated Saving Model (Recommended)

User perception: “Real saving” (bank-like boundary)

Behavior effect: protects money from accidental spending

Moves: dedicated pocket + labels + rules

Trade-off: slightly more friction to move funds

Merged Balance Model

User perception: “Wallet with perks”

Behavior effect: money stays spendable; saving stays shallow

Moves: same balance + interest/benefits overlay

Trade-off: adoption can be high, but saving intent stays weak

Recommendation

Recommendation: design AstraPay Tabungan as a separated saving experience (pocket + boundaries), and compete at fund relocation after payday (free transfers + allocation cues).

Learnings

  • “Tabungan” isn’t a label problem. It’s a boundary problem.
  • Adoption is ecosystem-driven; saving requires structure + trust cues.
  • Good discovery resolves forks with explicit trade-offs.
